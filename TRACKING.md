# Tracking

Everything the project knows it must do, has decided not to do yet, or has got wrong — **one file,
three record types and the causes behind the defects, four generated indexes**.

This replaced `ISSUES.md`, `BACKLOG.md` and `documents/design/open-questions.md` on 2026-09-08. They
were three files with three near-identical preambles, three copies of the slug rules and one script
invoked three ways. **The motive is portability rather than tidiness:** one file plus
[`scripts/genindex.py`](scripts/genindex.py) is a drop-in issue, backlog and question tracker for any
project using Scatterhoard, with no git hosting account and no separate tool. Three files plus a
script is a thing you port; one file plus a script is a thing you copy.

## The states, and why the division is load-bearing

The tracking surfaces divide by *state*, and the divisions are worth keeping sharp:

| The work is… | Tracked in |
|---|---|
| not yet decided | [Open questions](#open-questions), below |
| decided, not yet built | [Backlog](#backlog), below |
| built or buildable, not yet proven | [EARLY-VALIDATION.md](EARLY-VALIDATION.md) — still its own file |
| built, and wrong | [Issues](#issues), below |

**Sections in one file preserve that division nominally while making it much easier to file into the
wrong one.** That was the standing objection to unifying, and the answer is that a section is a *tag*
rather than a heading: an entry lands under the index its head memory's keyword names —
`hoard-proj-issue-entry`, `hoard-proj-backlog-entry`, `hoard-proj-question-entry` — and not under
whichever heading a human typed it beneath. A misfiled entry therefore appears in the wrong index,
where it is visible, rather than in the wrong part of a file, where it is not.

[EARLY-VALIDATION.md](EARLY-VALIDATION.md) is the one surface left outside. Its entries have never
been migrated into memory clusters, so folding it in would mean either a hand-written list inside a
generated file or a migration nobody has done; it tracks decided-but-unproven mechanisms that need
hands-on testing before being relied on. **Fold it in when its entries migrate, not before.**

Two neighbours are not tracking surfaces at all, and work is regularly misrouted to them:

- [STANDARDS.md](STANDARDS.md) — rules already followed.
- the `coding-lessons` memory set — how the *work* goes wrong, not how the *code* is wrong. A defect
  that reveals a recurring process failure earns an entry there as well as here.

## File as you go

**Append the entry the moment you notice, rather than carrying it in the session and hoping it
reaches the checkpoint.** Duplicates are cheap; a lost entry is not, and merging duplicates is work
for the day something is fixed rather than the day it is filed.

- **Defects.** Exercising the tools from a client is currently the most productive source of these,
  so file from the client session, as it happens.
- **Unbuilt work.** When you notice something decided-but-unbuilt, file it here rather than noting it
  in the document you happened to be editing. That habit is what this file exists to replace: before
  it, such work lived as asides inside documents about something else, accurate where they sat and
  invisible from anywhere else.
- **Questions.** A resolved question often leaves work behind, and that work becomes a backlog entry
  — decided, not yet built. Resolving a question and finding that nothing implements the answer is
  the normal case, not a discovery worth burying in the paragraph that records the resolution.

## How to use this file

Append; don't curate. Each entry carries a stable `slug`, so checkpoints, commits and memories can
reference it after the list has been reordered, and the slug is also the keyword its memories gather
on.

**Forming a slug.** Lowercase and hyphenated; **the same string as the memory keyword**, since the
slug is what gathers an entry's memories and two spellings split that gathering in half with nothing
to report the split. Name the thing, not its resolution — the defect rather than the fix, the missing
thing rather than the reason for it, the *question* rather than the answer you expect, so
`fixed-result-count` and not `result-count-should-be-fixed`. A file of open questions is the one
place where a handle can quietly settle something. Where the corpus already names *this entry* —
its own defect or question — use that handle rather than coining a second. **Where it names only the
entry's subject, do not take that term**: the slug is the keyword the entry's findings gather on, so
a subject term gathers the whole subject, and recalling the entry returns everything about it.
Coin a slug not yet in use, and link the entry to the subject's memories. `genindex.py --check`
reports a slug that was already a keyword well before its entry was filed
(`a-slug-that-is-also-a-subject-keyword-over-gathers`).

**Status is not marked by hand.** A row's `[x]` is generated from its head memory's status keyword,
so fixing, building or resolving an entry is recorded by superseding the head with the new standing
and regenerating. `genindex.py --check` fails if the file and the memories disagree. Completed
entries stay in the list — a fixed defect is evidence about where defects come from.

**Regenerating.** `python3 scripts/genindex.py TRACKING.md` rewrites all three regions; `--check`
rewrites nothing and exits non-zero when the file disagrees with the memories, so run it alongside
`checklinks.py`. Both read the **exported** memory file, so export first. **Never hand-edit between
the `BEGIN GENERATED INDEX` and `END GENERATED INDEX` markers** — the region is rewritten, and a
regeneration that would *remove* rows refuses, because the likely cause is a stale export rather than
a retired entry.

**This file's control marks live under `hoard-proj-`** — `hoard-proj-issue-entry`, `-issue-open`,
`-severity-*`, and the backlog and question families beside them — renamed 2026-09-07 into the
carve-out [`keyword-standards`](src/conventions/catalog.rs) licenses for a project's own tooling.
**Those names belong here; the rule behind them does not.** `keyword-standards` is served to every
Scatterhoard session, including those of people who have no copy of this repository, so restating the
prefix rule here would put a second copy where only one can be read — and this is the copy a user
never sees. Recall the convention rather than paraphrasing it.

## Entries and their memory clusters

An entry is a **row plus a cluster of memories**: the row is one line generated from the cluster's
head, and everything the entry knows lives in the memories. These rules govern writing that cluster —
when filing a new entry, and when migrating an existing one.

**Choose a slug that no memory would carry for any other reason.** The slug is the keyword the cluster gathers on, so a slug that doubles as a subject term gathers the whole subject instead of the entry's findings. Measured across the finished backlog on 2026-09-07: of 55 clusters, 37 hold two members or fewer, while `keyword-standards` returned 20, `investigation-pipeline` 17 and `graph-traversal` 16. The row is unharmed — its text is the head's opening — so this is invisible in the file and shows up only on recall, where *pull this entry's findings* answers with the subject's whole literature. Before coining one, recall it; if it already returns memories the entry did not produce, it is a subject keyword and needs a different name.

**Depth is earned by self-correction, not by how much happened.** A single-episode entry gets a head plus one or two members. The fuller treatment is for an entry that *corrects itself across dates* — a measurement later retracted as confounded, a diagnosis reversed, a fix replaced — because there, reading the cluster top to bottom puts the retraction after the number it retracts, and that ordering is the thing the members buy. Where nothing was retracted there is no ordering to preserve and the detail buys nothing, at roughly a thousand characters per member that every later recall pays for.

**Every member says in its own text when the thing happened.** Ordinarily `created` separates build-history from later observation; on a migrated cluster every member is minted on migration day, so that axis collapses exactly where the entry needs it. Say whether a member is history from implementing the item or an observation made afterwards while using it. Once the entry body is deleted, an undated member cannot be repaired from anything.

**Check present-tense claims before carrying them over; carry decisions across untouched.** An entry mixes two kinds of claim that age differently. *We chose X over Y because Z* stays true as history for ever. *The catalog has yet to catch up* decays silently, and nothing in the entry dates it, so it reads as current for ever — and migration mints it a fresh `created` date that makes it read as newly observed. Verifying every sentence would be prohibitive; verifying the present-tense behavioural ones is a handful per entry, and two false ones were caught this way in a single day. This is [`store-when`](documents/design/conventions.md)'s *name where it can be checked* applied to text written before that discipline existed.

**Store one batch per entry, head first, members in the order things happened — then check the returned ids ascend in the order you listed them.** Keyword recall orders by `matches DESC, id ASC`, and within a single keyword every hit scores 1, so id order *is* the narrative order a later reader gets. Nothing else reports a scrambled narrative and it cannot be fixed later without rewriting the memories. Batching a whole entry in one call was verified to preserve the order across roughly ninety entries.

**Delete the migrated body only after its memories are stored**, so an interruption leaves the file authoritative rather than the store.

**Read the echoed `summary` on every head.** It is the line the row will show. An opening like *"Fixed 2026-09-06, the same day."* is true, useless in a survey, and cheap to amend before export — after export it needs a supersession.

**And the row is more than the summary, none of which can be previewed.** It is assembled from the head's summary, its status and facet keywords, and its `depends_on` links, which [`genindex.py`](scripts/genindex.py) renders as `blocked by N`. There is no dry run: the generator reads the **exported** file, and exporting is exactly what makes the head immutable — so a row that comes out wrong costs a supersession rather than an amendment. **`depends_on` is the easy one to get wrong.** It means *this entry is blocked by that one*, not *this entry rests on that evidence*; a head that used it for the latter rendered as `ready · blocked by 1` on 2026-09-12, contradicting itself. Use `motivated_by` or `related_to` for evidence.

## Issues

Known defects in the built thing: something the code does that it shouldn't, or doesn't do that it
should. **Decided, implemented, and wrong** — which is the test for whether an entry belongs here.
Absent behaviour that was never written is not a defect; it is a backlog entry, and the distinction
is whether code exists to be wrong. Where a defect can't be fixed without settling a design question,
the entry links to the question rather than restating it.

Severity is by **consequence**, not effort:

| Severity | Meaning |
|---|---|
| **Corrupts** | Data is lost or silently wrong — including defects that *hide* whether corruption is happening. |
| **Blocks** | A caller cannot use the feature correctly without guessing. |
| **Misleads** | Works as built, and gives the caller a wrong belief. |
| **Costs** | Correct and honest, but wastes context or effort. |

State what's wrong, how it was found, what it breaks, and what "fixed" looks like. To file one, store
a head memory carrying `hoard-proj-issue-entry`, the slug, `hoard-proj-issue-open` and a
`hoard-proj-severity-*` facet; then export and regenerate. **If one of the [common
causes](#common-causes-of-defects) explains it, link the head `instance_of` to that cause** — this is
the moment the attribution is cheapest, because the defect is in front of you and the causes are in
this file.

## Backlog

Work that is **decided but not yet built**: the design settles it, nothing disputes it, and no code
does it. State what is already decided **and where**, what is missing, and what "built" would look
like. The first of those matters most — an entry that restates the design has become a second copy of
it, which is the failure this section was created to stop. Link to the decision; don't reproduce it.

Readiness is about dependency, not priority:

| Readiness | Meaning |
|---|---|
| **Ready** | Could be started now. Nothing is missing but the work. |
| **Blocked** | Needs a design question settled, or another item built, first. The blocker is named. |
| **Deferred** | Ready, and deliberately not being done yet. The reason is recorded and is expected to expire. |

**A caution specific to this section.** A backlog is the easiest of the four to fill with things
nobody decided — "we should probably…" is not a decision. If no design document settles it, it is an
open question. To file one, store a head memory carrying `hoard-proj-backlog-entry`, the slug, one
`hoard-proj-backlog-` status keyword and, while it is open, a `hoard-proj-readiness-*` facet; then
export and regenerate.

## Common causes of defects

Causes that explain several [issues](#issues), each with a structural fix worth more than any single
entry. **The rows are generated, ranked by how many issues each cause explains**, and nothing in this
section is written by hand, so no count in it can go stale.

A cause is a memory carrying `hoard-proj-cause-entry`, its slug and one standing,
`hoard-proj-cause-active` or `-retired`; a retired cause keeps its row, checked, because it is
evidence about where defects came from. Its opening line states the cause, and the rest names its
instances and the fix. **An issue is attributed by a link in either direction**: the issue's head
linking `instance_of` to the cause, which is what to write when filing a defect, or the cause linking
`causes` to the issue, which is how a cause takes on issues filed before it was recognised. A cause
found later is filed the same way — its head, with `causes` links to the issues that revealed it.
Any version of either chain counts, so marking an issue fixed never drops its attribution.

**The general form of a cause belongs in the `coding-lessons` memory set**, and the project's cause
links to it `instance_of` across sets: the project memory holds this project's instances, the lesson
holds what would be true on any codebase. Whether a cause is *common* is a count over this project's
issues and is inherently local; what the cause *is* usually is not. A project too young for patterns
can leave this region empty.
